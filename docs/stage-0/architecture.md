# Architecture proposal — decision pending

| Option | Strength | Cost |
|---|---|---|
| Strict TypeScript + React/Vite + Fastify/JSON Schema + SQL query builder | Shared boundary types, schema-driven OpenAPI, one UI, explicit SQL and familiar MySQL/MariaDB operations | Laravel rule semantics and ciphertext compatibility need dedicated tests; TS types do not replace runtime validation |
| Laravel API + React | Closest password, encryption and validation semantics, mature migration and queue ecosystem | Two language toolchains; runtime schema and generated client discipline still necessary |
| Go API + React | Explicit wire types, small deployable, operational affinity with Wings | More adaptation work for Laravel semantics; cross-language schema generation and worker plumbing |

Recommend first option, MySQL/MariaDB-compatible SQL, Redis queues/cache/fan-out, worker process and Docker Compose. Approve one primary engine/version before migrations; claim the second only once separately tested. Domain modules own tables and commands: identity/policy, nodes/Wings adapter, servers/allocations, catalog, files, backups, databases, schedules, activity/events and future automation. Dependencies point from transport to commands to ports. Only the adapter signs Wings credentials or makes daemon calls. REST, workers, remote callbacks and compatibility routes reuse authorization and transitions; use a durable outbox for transaction-to-queue handoff. Browser native UI uses same-origin API, with a separately qualified Wings WS/file transport. Build health/readiness and secret-free telemetry. Capture significant decisions as ADRs.

Stage 1 keeps one configurable working name, one shell, locked token palette, self-hosted Geist, Lucide, deterministic SVG primitives and five shared templates. Validate keyboard and responsive layouts in both languages at 360/768/1280/1920. Use translation keys and Intl formatting plus a native Indonesian reviewer and terminology glossary (server, node, backup, konsol, jadwal, alokasi). Set measured JS and load budgets in Stage 1; no assumed metrics. Generic profile never suppresses parity features; registry and override order from the brief apply at Stage 9.

## Compatibility policy

Recommended: native `/api/v1` with generated OpenAPI, plus stable aliases at original `/api/client` and `/api/application`, documented against the pinned Panel release. Same commands, different serialization and credential adapters. Preserve IDs, envelope, `include`/filters/pagination, HTTP statuses, error JSON and legacy auth/IP restrictions from source and golden fixtures. Do not invent elevated rights to match permissive upstream behavior. Start with Client list/detail, resource stats, websocket, power and command, then files/backups and other listed families; Application user/server CRUD including external-ID lookup, build/startup, suspend/reinstall, nodes/allocations, locations and nest/egg discovery plus database endpoints. Stage 8 must run an unchanged real integration.

Known gaps at proposal: no older-release guarantee; exact transformers, errors and Application ACL mapping are not yet characterized; direct pull is gated on egress; node configuration, DB password views and API credential creation conflict with a literal no-full-secret rule. Propose one-time out-of-band provisioning and tightly scoped secret delivery where parity requires it, with explicit user approval; never return stored API tokens or webhook URLs. Do not declare these routes compatible until resolved. No compatibility claim for undocumented plugins.
